# 原 SQL 保留与改写注释

用户要求：先在代码中完整保留并注释原 SQL，再写转换后的 SQL。代码评审者必须能在改写处看到原句和原因，不能只到 Git 历史或台账找原 SQL。

## 格式

每处采用“编号与语义说明 → 原 SQL 注释 → 活动 DM8 SQL”。说明针对实际差异，写明原意、改写原因、保持的业务口径；存在已知前提或真实人工结论时一并引用。静态检查没有执行证据时不写“达梦运行通过”。

下面仅演示注释格式。假设参数格式 `YYYYMMDD` 已由调用契约确定，表达式的含义是查询日期前一天：

```cpp
// DM8 适配 [SQL-示例]：仍取查询日期前一天；整数天运算和 DUAL 替代旧日期写法及辅助表。
// 原 SQL（保留追溯，不执行）：
// sqlstr = "SELECT TO_DATE(@DATE_TIME,'YYYYMMDD') - 1 DAY FROM SYSIBM.SYSDUMMY1";
// DM8 SQL：
sqlstr = "SELECT TO_DATE(@DATE_TIME,'YYYYMMDD') - 1 FROM DUAL";
```

实际处理时使用项目的真实条目编号和真实原句，不复制示例编号或推测参数格式。原 SQL 本来包含 DB2 等写法时标为“原 SQL”，不能因整体方向为 Oracle → DM8 就错误标成“原 Oracle SQL”。

## 完整性与注释语法

- C++、C#、TypeScript 的普通语句优先逐行添加 `//`，保留每行原文、字符串连接、变量和参数。SQL 文件使用其合法注释形式，其他配置采用宿主格式允许的方式。
- 多行赋值保留完整赋值和外层 SELECT 等部分，不能只保存改变的函数或 CTE。分散在条件分支里的 SQL 片段保留其拼接控制结构和对应原句，使改写前模板可恢复。
- 不支持注释的配置格式，不插入非法注释破坏解析；把完整原配置/SQL 放在紧邻的说明文件，关联稳定编号，在交付中说明该格式限制。
- 检查续行反斜杠、宏、嵌套注释和字符串边界，确保注释不会吞掉活动语句。应按宿主语法选择能完整保留原文的方式。
- 已有注释、未改写的兼容 SQL 无需制造重复历史块。同一 SQL 后续再次调整时保留最初原句一次，更新活动版本和理由，详细历史记台账。
- 原文若含真实凭据，注释和记录中的该值用 `<REDACTED>` 保留位置，不复制凭据。其余内容保持准确。

## 检查

把注释中的原句与可信的改前文件逐行核对；活动 SQL 与决定记录一致。注释只提供追溯，绝不用于恢复运行旧 SQL。全量扫描将这些原句标记为历史注释，活动残留统计只包括实际参与执行的代码。
